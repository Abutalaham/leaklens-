SECTION 01 / THE EXPOSURE GAP

Most leaks happen before you notice.

Sensitive values slip into shared archives, tickets, notebooks, exports, and commits long after the initial draft feels routine. Distinguishing ordinary text from high-risk tokens requires structured inspection before anything leaves your hands.

API keys Service and provider keys embedded in scripts, configs, or copied snippets.
Access tokens Short-lived or long-lived session and automation tokens left in local files.
Passwords Database, service, or staging credentials pasted during debugging.
Private keys Cryptographic or signing material included inside bundles or archives.
Personal information Email addresses, identifiers, and contact details inside reports or logs.
Sensitive metadata Document or file properties that reveal internal paths, authors, or origins.

SECTION 06 / PRIVACY & DEPLOYMENT REALITY

Security should not create another privacy problem.

Clear operational facts about how files, previews, redactions, and credentials are handled so you can evaluate your deployment accurately.

Local-first processing depends on deployment configuration

How scans run and which detectors or OCR modules are enabled depend on how your LeakLens instance is deployed and configured.

Processed by the configured LeakLens server

Submitted files are inspected by the configured LeakLens server rather than promised to never touch a server boundary.

Temporary storage & configured retention

Web scans use temporary storage according to your instance's configured retention settings rather than universal zero-retention.

Masked previews in findings

Findings display masked previews to reduce unnecessary raw value exposure during review.

Redaction creates a safer copy

Redacting selected findings produces a separate sanitised copy so you can review and share a cleaner version.

Rotation or revocation may still be needed

Redacting a file does not revoke credentials that were already exposed—rotate or revoke any real secret that may have leaked.

    Security Best Practices

    Never share real API keys or credentials. Commit .env.example files containing placeholders only. Keep actual credentials in your account-scoped vault or secure environment configuration.

    How the vault works

    New vault entries use per-entry Scrypt-derived keys and AES-256-GCM authenticated encryption before server-side storage. The server application can decrypt entries for password-protected portable exports; this is not a client-side or zero-knowledge vault. Portable exports use a separate password-derived Scrypt key and AES-256-GCM, and importing re-encrypts entries for the signed-in account.

    The vault listing returns variable names, categories, and masked previews only. Secret values are not returned by the listing endpoint.
